## Part A — Query DNS Records with dig

Resolver used: `192.168.0.1` (confirmed in the `SERVER:` line of every response, consistent with the earlier sections).

| Query | Status | Flags | QUERY/ANSWER Count | Query Time | Answer(s) | TTL |
|---|---|---|---|---|---|---|
| A | NOERROR | qr rd ra | 1/2 | 236 msec | `104.20.23.154`, `172.66.147.243` | 156s |
| AAAA | NOERROR | qr rd ra | 1/2 | 224 msec | `2606:4700:10::ac42:93f3`, `2606:4700:10::6814:179a` | 121s |
| MX | NOERROR | qr rd ra | 1/1 | 224 msec | `0 .` | 32s |
| NS | NOERROR | qr rd ra | 1/2 (+13 additional) | 216 msec | `elliott.ns.cloudflare.com`, `hera.ns.cloudflare.com` | 81s |

**Flag interpretation:** `qr` means this is a response (query/response bit set); `rd` means recursion was requested by the client; `ra` means recursion is available and was used by the resolver. No `aa` flag appears on any of these, correctly indicating `192.168.0.1` is a recursive/caching resolver, not authoritative for `example.com`, it asked Cloudflare's nameservers on the client's behalf.

**Record type explanations:**

| Type | Explanation |
|---|---|
| IN | The "Internet" query class (as opposed to legacy classes like CH/Chaos); virtually all modern DNS traffic uses IN |
| A | Maps a hostname to an IPv4 address (`example.com` → `104.20.23.154` / `172.66.147.243`, both Cloudflare edge IPs) |
| AAAA | The IPv6 equivalent of an A record, mapping the hostname to a 128 bit IPv6 address |
| MX | Identifies the mail exchange server responsible for accepting email for the domain, with a priority value (lower is preferred). The `0 .` answer here is a null MX record: it explicitly signals that `example.com` does not accept email at all, the priority is 0 and the target is the root domain `.`, a deliberate anti spoofing/no mail declaration (RFC 7505), not a misconfiguration |
| NS | Identifies the authoritative nameservers for the domain. `example.com` is delegated to Cloudflare (`elliott.ns.cloudflare.com`, `hera.ns.cloudflare.com`); the additional section opportunistically includes their A/AAAA glue records so a resolver doesn't need a second lookup just to reach them |

## Part D — Match Queries to Responses

| Transaction ID | Query Name | Type | Client/Resolver | Response Code | Answer(s) | TTL | Time Delta |
|---|---|---|---|---|---|---|---|
| `0x24a9` | `example.com` | A | Client: `192.168.0.102:36355` / Resolver: `192.168.0.1:53` | NOERROR (0) | `172.66.147.243`, `104.20.23.154` | 168s, 168s | 0.582089 s |

**Matching by transaction ID and endpoint tuple:** both frames carry transaction ID `0x24a9`, an exact match. The endpoint tuple also confirms the pairing: the query was sent `192.168.0.102:36355 → 192.168.0.1:53`, and the response returned `192.168.0.1:53 → 192.168.0.102:36355`, source and destination exactly reversed, which is the expected signature of a genuine reply to this specific query.

**Confirming the response source is the queried resolver:** the response's source IP (`192.168.0.1`) is identical to the resolver address the query was sent to. This confirms the reply came from the intended resolver and not from an unexpected or spoofed source.

**Calculating response time from frame timestamps:** response timestamp (21:21:58.932951) minus query timestamp (21:21:58.350862) equals 0.582089 seconds (approximately 582 ms).

**CNAME chains and multiple answers:** no CNAME chain is present; `example.com` resolves directly via A records with no alias hop. Two A answers were returned (`172.66.147.243` and `104.20.23.154`), both sharing an identical TTL of 168 seconds, consistent with both records belonging to the same RRset and expiring from cache together.

## Part E — Analyze DNS Generated by a Browser

67 packets were captured over the 40 second window. Rather than isolating a single browser page load, the capture reflects ambient background DNS activity from multiple running applications, a realistic scenario a forensic analyst frequently encounters, since modern desktop environments rarely produce traffic from just one source in isolation.

### Query Inventory

| Count | Domain | Type |
|---|---|---|
| 5 | `github.com` | A (1) |
| 3 | `portal.nelf.gov.ng` | A (1) |
| 2 | `portal.nelf.gov.ng` | HTTPS (65) |
| 2 | `github-cloud.s3.amazonaws.com` | HTTPS (65) |
| 2 | `github-cloud.s3.amazonaws.com` | A (1) |
| 1 each | `www.bing.com`, `user-images.githubusercontent.com`, `self.events.data.microsoft.com`, `nav-edge.smartscreen.microsoft.com`, `github.githubassets.com`, `github.com` (HTTPS), `collector.github.com`, `avatars.githubusercontent.com`, `assets-proxy.anthropic.com`, `api.github.com`, `alive.github.com` | A (1) and/or HTTPS (65) |

### Normal Variations Observed

- DNS type 65 (HTTPS/SVCB records) appears repeatedly alongside standard A records. This is a modern resolver feature where clients query for HTTPS service binding parameters (e.g. supported protocols, ALPN) in addition to the IP address, common in current browsers and not indicative of anything abnormal.
- Multiple queries for the same name (e.g. `github.com` ×5, `portal.nelf.gov.ng` ×3) reflect normal application behaviour, periodic polling, multiple simultaneous connections, or short TTL expiry forcing re resolution, not query flooding or malicious repetition.
- Third party CDN/asset domains (`githubusercontent.com`, `githubassets.com`, `s3.amazonaws.com`) appearing alongside the primary domain (`github.com`) is expected: a single logical "site visit" or application session commonly fans out to several supporting domains for assets, telemetry, and cloud storage.
- Unrelated domains from other applications (Microsoft telemetry/SmartScreen, Bing, Anthropic desktop assets) coexisting in the same capture window is a normal artefact of capturing at the interface level rather than isolating one process, it demonstrates why analysts must correlate DNS answers with actual subsequent connections (Part F) rather than assuming every query in a window belongs to one activity.

## Part F — Correlate DNS with Subsequent Connections

**Selected correlation:** `github.com`

| Step | Timestamp (Epoch) | Event |
|---|---|---|
| DNS answer | 1790109545.598423 | `github.com` resolved to `140.82.121.3` |
| TCP SYN | 1790109545.599438 | Client initiates connection to `140.82.121.3:443` |
| Time delta | +0.001015 s | Approximately 1 ms after resolution |

This is a clean, direct correlation: the client resolved `github.com` to `140.82.121.3` and initiated a TCP connection to that exact IP on port 443 (HTTPS) roughly one millisecond later, proving the DNS answer was actually consumed by the client, not just requested speculatively.

### Additional Correlations Observed (Supporting the Finding)

| Domain | Resolved IP | Connected IP:Port | Delta |
|---|---|---|---|
| `alive.github.com` | `140.82.114.25` | `140.82.114.25:443` | +0.0003 s |
| `collector.github.com` | `140.82.114.21` | `140.82.114.21:443` (×2 connections) | +0.012 s, +0.450 s |
| `api.github.com` | `140.82.121.5` | `140.82.121.5:443` (×2 connections) | +0.0005 s, +0.30 s |
| `self.events.data.microsoft.com` | `4.150.223.105` | `4.150.223.105:443` | +0.0004 s |

### Explaining the Mismatches

- `github.githubassets.com`, `github-cloud.s3.amazonaws.com`, and `www.bing.com` were resolved but show no corresponding TCP SYN in this window. This is expected, not anomalous: these are asset/CDN domains fetched conditionally (e.g. only if a cached local copy is missing) or by services that didn't complete a request within the 40 second capture. Legitimate causes include CDN edge selection deferring the actual fetch, browser cache hits eliminating the need to connect at all, or the connection simply occurring after the capture window closed.
- Several domains returned multiple A records (e.g. `github-cloud.s3.amazonaws.com` with 8 IPs) but the client only connected to one, normal DNS/CDN load balancing behaviour, where the client picks one candidate IP from the answer set rather than connecting to all of them.
- No IPv6/AAAA answers appeared in this capture, so no IPv4 versus IPv6 connection mismatch needed to be reconciled here.

## Part G — DNS Analysis Within SMTP Evidence

The Lab 4 SMTP capture (`smtp_working.pcap`) contains one DNS transaction preceding the mail traffic:

| Field | Value |
|---|---|
| Frame | 1 (query) → 2 (response) |
| Queried name | `mail.patriots.in` |
| Record type | 1 (A) |
| Resolved answer | `74.53.140.153` |
| Response name chain | `mail.patriots.in`, `patriots.in`, `patriots.in`, `patriots.in` |
| TTL values | 10827, 10828, 82828, 82828 (seconds) |

Before establishing the SMTP session, the client resolved `mail.patriots.in` to locate the mail server's IP address (`74.53.140.153`), this is the standard pattern of using an A record directly for the mail host (rather than an MX lookup on the bare domain), consistent with a client configured to connect to a specific named mail server rather than discovering it via MX delegation. The response name chain repeating `patriots.in` several times reflects multiple resource records returned in the same answer (e.g. accompanying NS or SOA adjacent records bundled in the response), each carrying its own TTL, the relatively long TTLs (up to approximately 23 hours for the 82828 second values) are typical for infrastructure records like mail server or domain NS entries, which change far less frequently than, say, a CDN fronted web A record.
